LoRA and QLoRA for Mixture-of-Experts (MoE) models
Yes, you can fine-tune an MoE model using LoRA or QLoRA without modifying its original pretrained expert weights. Depending on the configuration, you can attach separate trainable adapters to individual experts, shared attention layers, the router, or some combination.

The interesting part is that MoE models offer several fine-tuning strategies that dense models do not. You can specialize individual experts, train shared components, modify routing behavior, or even add new experts.

This distinction is especially important for your work on MoE expert offloading, tiered memory, and inference on GPUs with limited VRAM.

QLoRA does not mean that the adapter itself is necessarily 4-bit. Usually the pretrained model is quantized, while the adapter parameters and optimizer states use higher precision.

A subtle but important point: fine-tuning experts does not automatically make them subject-matter experts.

For example, suppose you fine-tune an MoE model on Rust programming examples. The model's router may send Rust-related tokens to many different experts, depending on their hidden representations.

If you attach adapters to all experts, the training signal is distributed according to which experts are activated.

You don't necessarily get an identifiable Rust expert afterward.

Creating an explicitly specialized expert requires additional architecture or training decisions, such as controlled routing, expert isolation, or training a new expert.

How gradients flow
Suppose an MoE layer has 64 experts and activates four for each token.

During a training step:

The router selects experts for each token.

Selected experts participate in the forward pass.

Gradients update LoRA adapters attached to those experts.

Unselected experts receive no expert-specific gradient contribution from that token.

Shared attention adapters receive gradients through the usual network paths.

Across a batch containing many tokens, potentially most or all experts may be activated.

If the router is frozen, it still determines which experts get training opportunities. This can lead to uneven adaptation, particularly with small datasets.

For this reason, I would start with a frozen router and collect expert-activation statistics before experimenting with router fine-tuning.

5. Where exactly are the fine-tuned weights stored?
There are three distinct meanings of stored.

A. During training
The adapter matrices reside in GPU memory when actively used, alongside their gradients and optimizer state.

The original pretrained weights are typically loaded in GPU memory, CPU RAM, or an offloaded storage hierarchy, depending on the training framework.

For example, conceptually, the tensor keys might resemble:

model.layers.0.mlp.experts.3.gate_proj.lora_B

model.layers.0.mlp.experts.3.down_proj.lora_B
Actual tensor names depend on the model and framework. Some MoE implementations pack all experts into a single 3D tensor, so the adapter may also be stored as packed tensors rather than separately named expert files.

The configuration records information such as rank, scaling, targeted modules, and base-model identity.

C. During inference
You have two deployment options.

Option A
Keep the adapter separate


Switch between adapters without duplicating the pretrained model. This is ideal for experimenting with multiple specializations.

Option B
Merge the adapter into the expert


Merge the learned update into the original weight matrix and save a new model checkpoint. This can simplify and accelerate inference but eliminates cheap adapter switching for that merged copy.

Merging is particularly relevant for MoE implementations. Hugging Face warns that some packed-expert LoRA paths materialize updates for experts that were not selected, causing significant inference overhead. Its documentation recommends merging when appropriate. 

Hugging Face
+1

For QLoRA, merging generally requires dequantizing or reconstructing weights at suitable precision, applying the updates, and optionally requantizing. The resulting quantized weights need not be bit-for-bit equivalent to dynamically applying the original adapters.

7. What does MoE-specific LoRA look like in code?
Hugging Face PEFT supports MoE expert tensors using target_parameters. This is important because some models represent all experts in a packed 3D nn.Parameter rather than separate nn.Linear modules. 

Hugging Face
+1

A representative configuration is:


from peft import LoraConfig

config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    target_parameters=[
        "mlp.experts.gate_up_proj",
        "mlp.experts.down_proj",
    ],
    task_type="CAUSAL_LM",
)


This illustrates shared attention adaptation plus expert adaptation. Exact parameter names must be checked against the loaded model.

One issue is that applying rank 16 to every expert can produce a substantial adapter. For a large expert count, you may want lower per-expert ranks, while retaining a higher rank for shared attention.

A more sophisticated implementation could allocate different ranks according to expert usage or measured importance.

8. Implications for your MoE expert-offloading architecture
This is where I think the approach becomes particularly interesting for your moe-microscope and MLOS work.

You could organize model storage into three independent layers:

Immutable pretrained model

Shared attention, routers, expert weight shards

Persistent HDD, SSD, or optical archive
Versioned adapter store

Rust adapter, ML adapter, FORTH adapter, etc.

SSD or system RAM, indexed by model/layer/expert
Active execution cache

Selected expert weights + selected adapters

GPU VRAM; optionally prefetch from RAM
Instead of storing complete fine-tuned copies of a 30B model, you could store one immutable base model and multiple adapter sets.

A possible logical cache key would be:

(
  base_model_hash,
  adapter_id,
  layer_id,
  expert_id,
  projection_id,
  adapter_version
)
This would allow you to experiment with:

Loading only the adapters associated with selected experts.

Sharing immutable expert weights among several specialized model variants.

Measuring adapter cache-hit rates separately from base-expert cache-hit rates.

Switching specialization without reloading the entire model.

Prefetching expert weights and their adapters together.

There is one complication: ordinary PEFT checkpoints and runtimes do not necessarily support independently loading each expert's adapter on demand. You would need an adapter-sharding layer and runtime integration, especially for fused expert kernels.

The biggest optimization opportunity may not be adapter storage itself, which is comparatively small, but coordinating adapter loading with expert loading so you avoid additional transfers and synchronization.

6. One more technique worth investigating: ACE
A particularly relevant 2026 development is ACE: Adapter Consolidation across Experts.

ACE identifies redundant expert-specific adapters and consolidates them into group-shared, higher-rank adapters. Its reported experiments show training speedups of 1.31–1.48× compared with expert-wise LoRA, without increasing peak memory. 

ACL Anthology

This is complementary to the LoRA-FA idea:

LoRA-FA reduces the memory cost of training adapter matrices.

ACE reduces redundant adapter specialization and fragmented execution across experts.

Combining their underlying ideas could potentially reduce training memory, adapter storage, and execution overhead, but would require a new implementation and validation.

How could I take an MoE model and fine tune it to be "better" at coding modern Rust, and then how can I measure/prove/demo that I succeeded?
Fine-tuning an MoE model to become demonstrably better at modern Rust
I would approach this as a controlled machine-learning experiment, rather than simply fine-tuning a model on Rust code and hoping it improves.

The goal is to produce an open-weight MoE model that is measurably better at writing, understanding, debugging, and modernizing Rust code, while preserving its existing general programming capabilities.

For your hardware and projects, I'd also want to demonstrate that the improvement can be achieved using LoRA, QLoRA, or LoRA-FA, without retraining the original experts.

The essential requirement is that the improvement be reproducible, statistically defensible, and visible in a live demonstration.

Rust is a particularly good target for fine-tuning experiments because the compiler, Clippy, Miri, and test frameworks provide unusually strong automated feedback.

However, compilation alone is not enough. A model that generates todo!(), excessive unwrap(), or incorrect implementations that merely type-check should not receive a high score.

I would distinguish three classes of Rust knowledge:

Language knowledge: ownership, borrowing, lifetimes, generics, traits, macros, async, pinning, associated types, const generics, and so on.

4. Use a three-stage training pipeline

Stage A: Supervised fine-tuning (SFT)
Train the model on examples of well-structured Rust implementations and successful refactorings.

This teaches the model what your preferred solutions look like.

Stage B: Preference optimization (DPO)
Construct pairs of solutions for the same request:

Preferred: correct, low complexity, well-separated responsibilities.

Rejected: correct but unnecessarily complex, tightly coupled, or impure.

The important part is that both should ideally pass functional tests. Otherwise, the model may merely learn to distinguish working code from broken code rather than learning your architectural preferences.

DPO can train the model to prefer the solutions that meet your standards without requiring a separate learned reward model.

Stage C: Optional reinforcement learning
Your grader provides an opportunity to use execution-based rewards.

For example, generate several solutions, run tests and grading, and reward successful implementations with fewer architectural violations.

This is more involved than SFT or DPO, so I would postpone it until you've demonstrated a measurable improvement from the simpler methods.

low     ← A mm x
update  ← B mm low

VeRA: An especially interesting alternative for X_eTaL-ML and MoE fine-tuning
VeRA (Vector-based Random Matrix Adaptation) is worth adding alongside LoRA, QLoRA, and LoRA-FA because it takes parameter sharing much further.

Instead of learning low-rank matrices for each adapted layer, VeRA uses shared, frozen random projection matrices and learns small scaling vectors.

For your projects, that creates three opportunities:

X_eTaL-ML: Express VeRA as matrix equations and left-to-right tensor pipelines, then expand them into executable APL-style code.

MoE fine-tuning: Share projection matrices across experts while allowing each expert to learn its own small adaptation vectors.

MoE expert offloading: Store extremely small expert-specific adaptations separately from the pretrained expert weights.

The third is particularly appealing. You could potentially have hundreds or thousands of adapted experts while keeping their task-specific parameter storage very small.

6. Where VeRA may not be as good as LoRA
VeRA's efficiency comes with tradeoffs.

Expressiveness: The fixed random projections restrict which weight updates can be represented. A sufficiently high-rank LoRA can learn directions that VeRA cannot.

Runtime computation: VeRA still performs two projections and two vector-scaling operations. Tiny checkpoint size does not automatically mean faster inference.

Quantization compatibility: A 4-bit base with VeRA is mathematically straightforward, but the particular PEFT backend and MoE implementation must support it. Do not assume that a QLoRA-style VeRA configuration works with every quantized model.

Expert specialization: Sharing random projections across experts may constrain their adaptations. The degree to which that hurts your Rust-specific fine-tuning is an empirical question.

Hugging Face currently documents VeRA for linear modules; support for packed MoE expert parameters should be verified separately.
